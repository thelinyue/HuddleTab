# v0.0.32 全新安装与从 v0.0.31 或 v0.0.30 升级

`v0.0.32` 支持全新安装和从 `v0.0.31` 原地升级，也保留从 `v0.0.30` 数据库升级的路径；不支持直接从更早版本升级。`v0.0.29` 与 `v0.0.30` 的数据库迁移记录相同，服务端无法单凭数据库区分两者；更早版本应先升级到 `v0.0.30` 并确认运行正常，再执行 `v0.0.32` 升级。

## 从 v0.0.31 或 v0.0.30 原地升级

活动删除已改为永久删除，不再提供“已删除活动”列表和恢复功能。升级会永久清理旧版本中所有已删除活动及其关联账单、结算、成员关系、邀请、通知和图片元数据，并移除 30 天恢复窗口。需要保留的活动必须先在旧版本恢复，再执行升级；遗留图片文件由现有孤立文件清理任务回收。

1. 使用 NAS / Docker 宿主的备份机制成套保护 PostgreSQL 数据、应用数据目录（包括上传文件和 `app-secret`）、Compose 文件、`.env` 与部署密钥，记录旧镜像版本。不要删除或修改 `_sqlx_migrations`。
2. 在旧版本中完成所有未同步离线账单和附件，尤其是早期版本留下的 File/Blob 格式附件。`v0.0.31` 只读取当前 ArrayBuffer 格式的离线附件；旧格式记录会显示为无法恢复，需要重新选择或移除。升级时不要清理浏览器站点数据，以免丢失其他未同步草稿。
3. 保留原 PostgreSQL、应用数据目录和认证密钥，更新目标镜像后运行：

   ```bash
   docker compose pull
   docker compose up -d
   docker compose ps
   ```

4. 服务在监听 HTTP 前检查完整的 `v0.0.30` 八条历史迁移记录，只执行后续迁移，不重建表。后续迁移会处理旧邀请并永久清理已删除活动，保留其余活动和用户数据。若记录缺失或出现未知版本，服务拒绝启动；应恢复匹配的备份，不要伪造迁移记录。登录后核对活动、账单、附件及管理员设置，重启后确认数据仍在。

## 全新安装

1. 为新安装准备独立部署目录和空数据库。将 `DATA_HOST_DIR` 设置为新的空目录；PostgreSQL 和应用分别使用新目录下的 `postgres`、`app`。外置 PostgreSQL 必须使用新的空数据库，不复用旧上传目录或认证密钥。
2. 按 NAS 宿主用户设置 `PUID`/`PGID`，未设置时默认 `10001:10001`。拉取并启动目标镜像：

   ```bash
   docker compose pull
   docker compose up -d
   docker compose ps
   ```

3. 服务执行单份新安装迁移并记录 SQLx 版本；重复启动不会重新建表。从管理员配置或首次启动日志获取凭据，检查登录、活动创建和附件功能。

新安装若沿用旧域名，应先处理旧部署的未同步草稿，再清理该站点的 Cookie、IndexedDB、缓存和 Service Worker；已安装的 PWA 也应移除并重新安装。全新安装与旧部署的数据独立，不提供自动合并。

## 恢复

恢复备份时应成套恢复对应版本的数据库、应用数据、配置和密钥。`v0.0.31` 与 `v0.0.30` 备份可在本升级边界内恢复；更早版本的备份须先使用其匹配镜像恢复并升级到 `v0.0.30`。宿主操作见 [数据保护与恢复](data-protection.md)。
