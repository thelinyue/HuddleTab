# 加入活动时认领临时成员

## 编码前场景推演

1. **直接认领**：所有者先用临时成员记录付款、分摊和结算；用户打开有效邀请，登录后选择该成员并确认。事务只绑定原成员的账号并推进版本，保留成员 ID、昵称、角色、加入时间及全部账务引用。邀请使用次数、通知、审计与活动 revision 同步提交；重放不重复写入。
2. **审批认领**：活动要求审批时，用户选择临时成员后只产生待审批申请。所有者在成员面板或通知中看到申请人的账号昵称和认领对象；批准后绑定原成员，拒绝不改变成员。相同目标的重复提交返回原申请，不允许静默替换待审批目标。
3. **受邀注册**：匿名预览仅显示活动概况。注册只创建账号并保留邀请上下文，回到加入页后再选择新成员或临时成员；不会在选择前自动生成另一个账务身份。已有活动成员（包含 LEFT）继续使用原身份加入，不提供身份合并。
4. **多人竞争**：待审批申请不占用临时成员。两个账号可以申请同一身份，由所有者判断；活动行锁串行化最终绑定，只有一个账号成功。成功绑定（包括现有定向绑定流程）或成员被移除时，相关其他待审批认领申请自动作废，并同步通知双方。
5. **目标失效**：成员列表加载失败时保留页面并重试；确认时发现目标已绑定、移除或跨活动则拒绝并刷新候选，不自动改为新成员加入。邀请撤销、过期或活动不再 ACTIVE 时沿用现有拒绝规则。

## 实现边界

- 认领跟随活动加入设置；直接加入模式下有效邀请即为认领授权。
- 候选仅对已登录且持有有效普通加入邀请的用户开放，按稳定成员 ID 选择，默认作为新成员加入，不按昵称自动匹配。
- 现有定向绑定邀请仍固定目标，不允许请求覆盖；保留其已有所有者批准语义。
- 使用现有成员、申请、邀请、通知、审计和 revision 模型，不增加占用、离线认领或账务合并机制。
- 认领当下保留临时昵称，之后用户改昵称仍遵循现有账号同步规则。

## 验收

PostgreSQL 验证历史引用、审批、重复请求、竞争、作废及失败无副作用；前端验证注册后确认、成员单选、请求字段、失败重试和缓存刷新。浏览器验证直接及审批流程，并检查 320px、390px 和桌面视口、长昵称、键盘操作及无横向溢出。
