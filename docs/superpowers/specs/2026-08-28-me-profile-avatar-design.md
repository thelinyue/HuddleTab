# HuddleTab “我的”模块与头像预设设计

> 状态：待书面确认
>
> 日期：2026-08-28
>
> 视觉基准：用户提供的“我的 / 个人资料 / 邮箱 / 修改密码 / 主题 / 系统管理”移动端设计图

## 1. 目标

本次重构将“我的”从单页 Overlay 编排改为清晰的主页与二级页面，同时让用户可以从现有六张本地头像中选择一张作为账户头像。

成功标准：

1. “我的”主页与参考图的信息层级、分组方式和视觉密度一致。
2. 个人资料、邮箱、修改密码和主题使用可直接访问的二级路由。
3. 用户选择的头像跨设备保存，并在所有正式成员身份中保持一致。
4. 新注册用户和新建的首位管理员默认使用 `avatar-02`。
5. 现有用户在主动选择前继续使用当前稳定哈希头像，不因迁移改变外观。
6. 临时成员继续使用稳定哈希头像，不引入不存在的账户资料。
7. 不改变账务、权限、离线 Mutation、邀请和活动生命周期逻辑。

## 2. 范围

### 2.1 页面

- `/me`：我的主页。
- `/me/profile`：个人资料与头像选择。
- `/me/email`：绑定或更换真实邮箱。
- `/me/password`：修改密码。
- `/me/theme`：主题选择。
- `/admin`：沿用现有系统管理首页，只调整为与参考图一致的移动端列表样式。

### 2.2 明确不做

- 不实现上传、自定义裁剪或外部头像 URL。
- 不实现参考图之外的新账户字段。
- 不展示 Synthetic Email。
- 不新增当前系统没有真实能力的管理入口。
- 不改变 System Admin 与活动权限的隔离规则。
- 不把头像写入 `activity_members`，也不复制到每个活动。

## 3. 头像数据模型

在 `user_profiles` 增加可空整数列：

```text
avatar_preset INTEGER NULL
CHECK (avatar_preset BETWEEN 1 AND 6)
```

该列不设置数据库默认值，迁移后历史数据保持 `NULL`。显示规则为：

```text
真实 imageUrl（未来能力）
→ 用户已选 avatar_preset
→ 按稳定 ID 哈希分配现有六张头像
```

新用户默认值不由数据库隐式填充，而由两个创建入口显式写入 `2`：

- 普通注册 `RegistrationService`。
- 首次初始化管理员 `initialize-setup`。

这样可以同时满足“新用户默认 avatar-02”和“现有用户不被批量改头像”。

## 4. 头像传播规则

账户头像属于 `UserProfile`，不属于 ActivityMember 账务身份。正式成员查询通过：

```text
activity_members.user_id
→ user_profiles.user_id
→ avatar_preset
```

需要头像的成员 DTO 增加向后兼容字段：

```ts
avatarPreset?: number | null;
```

覆盖范围：

- 成员列表与成员管理。
- 快速记账、付款人与分摊设置。
- 结算总览、推荐转账与结算记录。
- 消费详情与分摊明细。
- “我的”主页和个人资料页。

临时成员 `user_id` 为空，`avatarPreset` 返回 `null`，继续按 ActivityMember ID 稳定映射。头像变化是展示偏好，不增加 Activity Revision，不写账务 Audit，也不改变离线 Mutation 格式。

## 5. API 设计

### 5.1 读取资料

`GET /api/me/profile` 在现有响应上增加：

```ts
{
  avatarPreset: 1 | 2 | 3 | 4 | 5 | 6 | null;
  maskedEmail: string | null;
  emailVerified: boolean;
}
```

`maskedEmail` 仅在 `email_kind = REAL` 时返回脱敏结果；Synthetic Email 始终返回 `null`。`emailVerified` 读取认证用户的真实状态，不能根据 `emailBound` 推断。

### 5.2 保存个人资料

沿用 `PATCH /api/me/profile`，支持：

```ts
{
  nickname: string;
  avatarPreset?: 1 | 2 | 3 | 4 | 5 | 6;
}
```

`avatarPreset` 保持可选，以兼容现有只修改昵称的调用。服务端使用 Zod 白名单校验，不能由客户端提交任意文件路径。

### 5.3 其他账户 API

- 邮箱继续使用 `POST /api/me/email`。
- 密码继续使用 `POST /api/me/password`。
- 主题继续使用 `PATCH /api/me/theme`。
- 退出登录继续使用 `POST /api/auth/sign-out`。

不新增重复端点。

## 6. 页面设计

### 6.1 我的主页

- 顶部标题“我的”。
- 浅薄荷色资料卡展示头像、昵称、`@username` 和可选“系统管理员”标签。
- “账户与安全”分组包含个人资料、邮箱、修改密码。
- “偏好设置”只包含主题。
- System Admin 才显示“管理”分组和系统管理入口。
- 退出登录只出现在主页，不出现在任何二级资料页。
- 底部显示真实产品版本文案并保留全局底部导航。

列表采用紧凑圆角边框组，行高不低于 `56px`，交互热区不低于 `44px`。使用语义 Token 映射亮暗主题，不在组件内新增散落颜色。

### 6.2 个人资料

- 顶部返回按钮与标题“个人资料”。
- 大头像作为当前选择预览。
- 六张头像以可键盘操作的单选网格展示，选中状态同时使用边框、勾选标记和 `aria-checked`，不只依赖颜色。
- 昵称可编辑。
- 用户名只读，并明确说明其为系统唯一标识。
- 保存按钮一次提交昵称和头像选择。
- 保存失败保留全部输入并显示字段附近的中文错误；成功后返回“我的”主页并刷新资料。

### 6.3 邮箱

- 未绑定状态显示用途说明和“绑定邮箱”。
- 已绑定状态只显示脱敏邮箱和验证状态，不返回完整邮箱。
- “更换邮箱”复用现有绑定接口和服务端校验。
- 不伪造邮件验证流程；当前 `email_verified` 的真实状态按现有能力展示。

### 6.4 修改密码

- 当前密码、新密码、确认新密码。
- 确认值只用于客户端一致性校验，不改变服务端密码 API。
- 保留正确的 `autocomplete`、密码管理器和粘贴能力。
- 提交时禁用按钮并显示进度；成功后给出明确反馈。

### 6.5 主题

- 跟随系统、浅色模式、深色模式三个原生 radio 语义选项。
- 选择后继续由服务端保存偏好，再更新本地主题，避免显示与资料不一致。
- 主题入口和退出登录不在个人资料页重复出现。

### 6.6 系统管理

系统管理首页仅映射现有真实页面：

- 用户管理 `/admin/users`。
- 系统设置 `/admin/settings`。
- 备份与恢复 `/admin/backups`。
- 系统信息 `/admin/system`。

不新增参考图中名称相近但没有独立落地能力的入口。服务器权限守卫继续作为最终授权边界。

## 7. 组件边界

- `MemberAvatar` 增加可选 `avatarPreset`，真实 `imageUrl` 仍保持最高优先级。
- 新增轻量 `AvatarPresetPicker`，只负责六张本地资源的单选语义，不处理网络保存。
- 二级页面共享一个简单的返回标题栏；不为单次布局创建通用页面框架。
- “我的”主页继续复用现有设置行结构，但按参考图调整表面、间距与状态样式。

关键组件补充中文注释，说明头像优先级、历史用户兼容和正式成员传播规则。

## 8. 数据流

### 8.1 读取

```text
进入页面
→ GET /api/me/profile
→ 渲染当前 nickname / avatarPreset / email 状态 / theme / role
```

### 8.2 保存头像

```text
选择六张预设之一
→ 本地预览
→ PATCH /api/me/profile
→ 服务端校验 1..6
→ 更新 user_profiles
→ 返回“我的”主页并重新读取资料
```

### 8.3 活动内展示

```text
活动页面读取成员 DTO
→ USER 成员携带 avatarPreset
→ GUEST 成员为 null
→ MemberAvatar 按统一优先级渲染
```

## 9. 错误与兼容

- 非法头像编号返回可理解的 `422` 中文错误。
- 资料不存在保持现有 `404 PROFILE_NOT_FOUND`。
- 资料保存失败不清空页面输入。
- 旧客户端不提交 `avatarPreset` 时仅更新昵称。
- 历史用户 `avatar_preset IS NULL` 时继续稳定哈希，不出现空头像。
- 新增 DTO 字段为只读可选字段，不修改现有写入契约。

## 10. 测试策略

按 TDD 分层覆盖：

1. Schema/Migration：字段可空、范围约束、历史行保持 `NULL`。
2. Registration/Setup：新用户和首位管理员显式保存 `avatar-02`。
3. MeService/API：读取、保存、非法编号、旧昵称请求兼容、Synthetic Email 不泄漏。
4. MemberAvatar：真实图片、用户选择、稳定哈希三层优先级。
5. 成员 DTO：正式成员传播选择，临时成员保持 `null`。
6. UI：主页信息架构、二级路由、六头像单选、保存失败保留、密码确认、主题和退出登录归属。
7. E2E：登录后进入主页、修改头像、跨页面显示、刷新后保留。

不新增像素快照 gate。视觉通过真实截图人工核对。

## 12. 实施边界

- 不修改金额、分摊、Ledger 或 Settlement 算法。
- 不修改 ActivityMember 的账务身份语义。
- 不修改权限矩阵、邀请 Token 生命周期或离线 Mutation。
- 不删除现有认证与数据安全措施。
- 只修改与“我的”模块、头像资料和正式成员头像投影直接相关的文件。
